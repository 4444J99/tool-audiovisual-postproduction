# Short-film demo: the whole chain from one command

`tools/short_film_demo.py` runs every stage of the synthetic chain ([PIPELINE-CHAIN](PIPELINE-CHAIN.md): set spec, shot plan, coverage, room-tone fill, loudness delivery, colour plan, captions, caption burn-in, delivery QC), verifies the chain, and muxes its burned-in frames and delivered dialogue into one small mp4. The mp4 is then judged against the sealed chain. Everything is invented; nothing is played (ffmpeg only writes and reads files, no audio device and no browser).

## Command

```bash
python tools/short_film_demo.py run --output outputs/short-film-demo
python tools/short_film_demo.py verify --output outputs/short-film-demo
```

Needs NumPy and SciPy (the chain's loudness stage) and an ffmpeg with `libx264` and `aac`. `outputs/` is git-ignored, so the output is scratch. `--delivery` (a preset or spec JSON) and `--qc-spec` pass through to the chain. A non-empty `--output` is refused and left alone unless it holds the `.short-film-demo` marker. The demo builds in a hidden sibling directory and swaps it in with a rename only once the chain, the mp4 and every check have passed, so a failed run leaves an earlier output exactly as it was (and a first run leaves nothing at the path); a marked directory is replaced by that swap, never deleted first. An `--output` that is or contains the working directory, the repository, the home directory or the filesystem root is refused up front (exit 2, JSON) with nothing deleted; the comparison is by device and inode, so a differently cased spelling on a case-insensitive volume is refused too. An interruption (Ctrl-C, or SIGTERM, which `run` turns into exit 143 for the duration of the run) between the two renames puts the old output back, so `--output` always holds either the old output or the new one. A run killed outright (SIGKILL, power loss) between the two renames leaves `--output` missing and the previous output only as a hidden `.<name>.old-*` directory, which can be the only copy: the next run restores the newest marked one to `--output` before doing anything else (reported as a `warning`) and never sweeps a `.old-*` while `--output` is missing. A killed run can also leave hidden `.<name>.build-*` or `.<name>.old-*` directories beside the output; the next run to that output removes the ones older than an hour (the name pattern and age are the proof, so a directory that lost its marker to a partial removal is reclaimed too). The marker on an existing output is checked again immediately before the swap, and a run that finds it gone refuses (exit 2, JSON) and leaves the directory untouched. An interruption after the second rename keeps the new output and removes the retired one at once. Concurrent runs to the same output are not locked against each other (known limit). A removal that fails (a read-only subdirectory it cannot unlock) is reported as `warnings` in the JSON summary and leaves that directory for the next run to sweep.

## What it writes (`outputs/short-film-demo/`)

| File | What it is |
|---|---|
| `short-film.mp4` | 26.5 s, 240x48, exactly 24 fps, 636 frames, H.264 (lossless, yuv420p) + AAC 16 kHz mono (the 8 s of delivered dialogue, padded with silence to the picture length). About 145 KB. |
| `demo-hashes.json` | SHA-256 of every file written, the chain hash, the stage list and the ffmpeg build that made the mp4 |
| `demo-qc.json` | the mp4 judged against the chain (below) |
| `qc/qc-report.json` | the chain's own delivery QC ([DELIVERY-QC](DELIVERY-QC.md)) |
| everything else | the chain's artefacts, listed in [PIPELINE-CHAIN](PIPELINE-CHAIN.md) |

`verify` compares every field of `demo-hashes.json` it can: the schema, chain hash, stage list and the four `deterministic` hashes against the sealed chain, the `encoder` note and that `encoder.ffmpeg` is an ffmpeg version line (it is not compared with the ffmpeg verifying, since another build may legitimately verify the same mp4), the file hashes, and `mp4_sha256`. It also re-judges the mp4 and requires `demo-qc.json` to equal that judgement (floats within 0.05). `demo-qc.json` and the marker are left out of the file hashes, so the `demo-qc.json` comparison is what covers it. Every failure of `run` or `verify` (a malformed hash file, a remux, an output path that is a file or a symbolic link, an unreadable marker) exits 2 with the problems as JSON.

`demo-qc.json` checks: an MP4 container (a Matroska or other remux is refused); one video and one audio stream; H.264 at the burn-in geometry and the ledger's exact frame rate; AAC 16 kHz mono; container duration equals the final ledger's seconds; frame count equals the ledger's; **the decoded luma plane equals `captions/frames.y8` byte for byte** (the video is lossless); the stream is `yuv420p` with limited or unflagged range, square pixels and no colour matrix, transfer or primaries flags (the chroma check reads the stream as it is, so a 4:4:4, full-range or re-flagged stream is refused rather than averaged back to grey); the decoded chroma planes are flat grey (every U and V value within 1 of 128); the mp4's audio measures within 1 LU of the delivered dialogue (AAC is lossy, so this is a tolerance, observed -22.93 against -23.00 LUFS); the mp4's sound is the delivered dialogue, at least 15 dB SNR against `dialogue-delivered.wav` after alignment within 512 samples (a clean encode measures about 33 dB with lag 0, noise at the same loudness about -3 dB); every 100 ms block of the dialogue louder than -50 dBFS is there at least 6 dB SNR, a shorter final block included (an honest encode measures 12.9 dB in the first block and 22 dB or more elsewhere; the demo's 8 s of dialogue is whole blocks, so the partial-block rule is exercised only by the unit tests), so a muted, replaced or overlaid stretch cannot hide in a whole-track figure; and the padding stays below 0.003 full scale for the first 1024 samples after the dialogue (AAC rings at most 0.0003 there) and below 0.001 after (the clean demo is exactly zero). Bounds, not proofs: sound quieter than about -15 dB relative to the dialogue, laid under it, still passes. A tone or noise added where the dialogue is not, or sound that is not the dialogue at the right loudness, fails here even when `demo-hashes.json` has been re-sealed.

The chain and QC hashes are asserted too. They used to differ between Linux CI runs of one commit while the frames, dialogue and captions did not. The cause: the room-tone fill report sealed a hash of the fill's float64 audio *before* 16-bit quantisation. The last bits of those floats come from the host's FFT and libm, so another CPU or library build changed the report, the stage and the chain hash while the written WAV stayed byte-identical. The chain now derives the fill report (its output hash and its measured levels) from the 16-bit samples it writes, and `tests/test_chain_determinism.py` moves the fill's synthesised floats by up to a few hundred ulps and requires every written file to stay identical (the QC report did not change under that drift before the fix either). What this cannot promise: a drift large enough to flip a sample's 16-bit rounding, or a value measured exactly on a rounding tie, would still change a hash. The same holds for the rounded metadata the fill report keeps from the float synthesis itself, which is not re-derived from the 16-bit samples: each hole's `gain_db` and `target_dbfs` (two decimals) and the clamp warnings (the tone gain printed to 0.1 dB, and whether the gain was clamped at all). They come from float64 levels (`target / rms(bed)`), so a host whose FFT or libm differs enough to move one across a rounding step or the clamp limit would change `fill-report.json` and with it the chain and QC hashes, while the WAV could stay identical. The determinism test moves the floats by a few hundred ulps, far too little to cross such a step on this input. NumPy and SciPy are not pinned exactly by this repository.

The mp4 hash is likewise not pinned anywhere: it depends on the ffmpeg, libx264 and AAC encoder build, so another build may write different bytes for the same picture and sound. What does not change is `mp4.luma_equals_burnin`, which ties the picture to `frames.y8` whatever encoder wrote it. Encoding uses `-threads 1`, bit-exact flags, no metadata and `-qp 0`, which is what makes the bytes repeat on one build.

## What the test asserts

`tests/test_short_film_demo.py` runs the command twice into two directories and asserts: both exit 0 and print the same summary; `demo-hashes.json`, the mp4 and every other written file are byte-identical across the two runs, and again from another working directory, a relative output path and a changed `PYTHONHASHSEED`, `TZ` and locale (chain and QC hashes included); the whole twelve-stage chain ran and its QC report passes; every mp4 check passes; `verify` accepts a fresh run; a flipped mp4 byte, an edited caption, and a lossy re-encoded mp4 whose hash file was re-sealed (named by the decoded-luma check) are each refused; a foreign non-empty directory, including one with a stray `demo-hashes.json`, is refused untouched; a refused run does not lock its directory; a rerun over its own output gives the same hashes; a delivery spec the audio cannot meet (`streaming`) writes no mp4; and the chain, QC, frames, delivered-dialogue and captions hashes in this document are the ones the run produces. The test is skipped where ffmpeg lacks `libx264` or `aac`.

## What this does not show

That the film looks or sounds good (the picture is a 5x7 test font over an invented ramp; the dialogue is a synthetic stand-in), that the mp4 meets any distributor's specification, or how a player renders it. It shows the files the chain sealed are the files in the mp4, and that the whole run repeats.
